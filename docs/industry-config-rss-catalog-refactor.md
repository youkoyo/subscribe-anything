# 管理员产业信息配置与预置 RSS 源库重构提案

> 状态：讨论稿
>
> 目标：让不熟悉监测、数据源和调度配置的管理员，也能用自然语言快速创建一个可用的产业信息池；优先复用经过治理的 RSS 源，只有在覆盖不足时才调用 AI 找源和生成脚本。

## 1. 背景与结论

当前“新增产业配置”页面把三类不同性质的工作放在同一张表单中：

1. 定义产业与监测目标；
2. 定义信息源和信息池边界；
3. 设置订阅审批与邮件报送运营规则。

这对普通管理员的隐含要求过高：他需要在还不知道有哪些合适信息源、也不知道配置最终效果前，先填写关键词、风险词、地域、实体、源类型、报送时间和时区等字段。实际 API 只强制要求“产业名称”，但界面把大多数字段呈现为同等重要的必填式决策。

建议采用两个互相配合的改变：

- **创建产业配置改为“简要描述 → 系统补全 → 审核后构建”**，默认只要求管理员说明“要关注什么”。
- **把 `feeds-zh.opml` 治理成预置 RSS 源库**，在发现源阶段先匹配、验证和复用这些可直接订阅的源；只有覆盖不足时才回退到现有 AI 发现和脚本生成流程。

这不是删除现有 AI 能力，而是让 AI 从默认路径变为“补齐长尾来源”的能力：成本更低、结果更稳定、管理员也更容易理解。

## 2. 现状诊断

### 2.1 表单的认知负担

当前创建页在一个页面内展示以下决策：

- 产业名称、行业分类、细分领域、关注级别、产业说明；
- 关键词、风险词、区域、关注对象；
- 权威 / 新闻 / 社媒 / 公众号 / 自有补充五类来源；
- 订阅模式、每封邮件条数、发送时间、时区、两个运营开关。

主要问题如下。

| 问题 | 对管理员的影响 | 重构原则 |
| --- | --- | --- |
| 字段按数据结构排列，而非按任务排列 | 不知道先写什么，也不知道哪些会影响找源 | 用任务语言组织：关注什么、优先看什么、何时通知 |
| 所有配置前置 | 还未看到候选源就要做来源与报送决策 | 先产出候选方案，低频配置后置 |
| “来源类型”混合来源性质与使用目的 | 管理员难判断该不该勾选公众号或社媒 | 改为“信息源偏好”，并说明其用途与默认权重 |
| 四个自由文本框没有示例或建议 | 不知道关键词与风险词应写多细 | 支持自然语言描述，由系统拆分成可审阅标签 |
| 报送与订阅规则干扰建池 | 普通管理员可能只想先建池 | 使用可靠默认值，放入高级设置或创建后配置 |
| `*/1 * * * *` 作为可选报送时间 | 容易被误选为生产配置 | 仅在调试模式或显式“测试设置”中提供 |

### 2.2 现有发现源 / 生成脚本链路的机会

当前链路是“AI 发现来源 → 人工选源 → 每个来源 AI 生成并验证脚本”。它对未知网站有效，但对已经是标准 RSS/Atom 的来源成本偏高：同一类 RSS 解析脚本被反复生成、反复做 LLM 质检。

预置 RSS 库应成为这条链路前面的第一层：

```text
管理员描述产业
  → 系统生成监测画像
  → 匹配预置 RSS 源库并即时验源
  → 候选源足够：使用通用 RSS 采集器，跳过 AI 脚本生成
  → 候选源不足：AI 发现补充来源
  → 仅对非标准 / 非预置来源生成并验证脚本
```

## 3. 目标体验

### 3.1 创建时只做三件事

创建页改成一个“快速建池”入口，默认只展示：

1. **产业 / 主题名称**：例如“食品安全与连锁餐饮经营影响”。
2. **想持续关注什么**：可用一段自然语言填写，例如“监管抽检、处罚、召回，以及它们对连锁餐饮品牌的影响”。
3. **信息源偏好**：以可多选的卡片呈现，并提供“推荐组合”。

建议的偏好项：

| 偏好 | 说明 | 默认用途 |
| --- | --- | --- |
| 权威事实优先 | 政府、国际机构、权威媒体；低噪声 | 主来源 |
| 主流新闻覆盖 | 事件覆盖和时效性 | 主来源 / 补充 |
| 行业与商业洞察 | 行业媒体、财经商业媒体 | 补充 |
| 技术与专业信息 | 科技、开发者、研究类来源 | 补充 |
| 热点与舆情线索 | 热榜、社媒、聚合平台 | 仅发现线索 |
| 公众号 / 作者观点 | 垂直洞察和观点 | 低权重补充 |

系统默认选择“权威事实优先 + 主流新闻覆盖”，并根据产业名称推荐其余选项。管理员不需要了解 RSS、脚本、cron 或数据表字段。

### 3.2 创建后给出可审核的“监测方案”

点击“生成监测方案”后，系统展示一个可编辑的审核页，而不是直接进入复杂向导。页面包含：

- 系统提炼的关键词、风险词、地域与关注对象；
- 已匹配的预置 RSS 源，按偏好分组并显示可信度、用途和最近健康状态；
- 缺口说明，例如“没有找到地方监管处罚源，建议进行 AI 补充搜索”；
- 两个明确操作：**用这些来源开始构建**、**补充搜索更多来源**。

高级设置（订阅审批、邮件条数、发送时间、时区、扩展申请）移到“发布与报送设置”折叠区，使用安全默认值。创建后仍可在产业配置详情中修改。

### 3.3 信息源偏好不是简单分类

“信息源偏好”描述的是来源在信息池中的角色，而不是文章主题。建议将来源至少标为：

```ts
type SourcePreference =
  | 'authoritative' // 权威事实
  | 'mainstream'    // 主流新闻
  | 'business'      // 财经与商业
  | 'industry'      // 行业与专业媒体
  | 'developer'     // 技术与开发者
  | 'research'      // 知识、研究、深度解读
  | 'trend'         // 热点、社媒、聚合线索
  | 'creator';      // 公众号、作者观点

type SourceUsage = 'primary' | 'supplementary' | 'discovery';
type TrustLevel = 'high' | 'medium' | 'low';
```

这样，“微博热搜”和“新华社”都可能命中“食品安全”，但前者只能提示线索，后者可作为事实依据。后续摘要、排序与告警也应使用这组标签。

## 4. `feeds-zh.opml` 预置 RSS 源库方案

### 4.1 初始资产

该 OPML 文件包含 **204** 个不重复的 RSS 地址，原始内容分类分布如下：

| 原始分类 | 数量 | 初始归类建议 |
| --- | ---: | --- |
| 新闻 | 28 | 主流新闻 / 权威事实（按发布者再细分） |
| 科技 | 28 | 行业与专业、技术与开发者 |
| 知识 | 9 | 研究与深度解读 |
| 娱乐 | 2 | 主流新闻或热点线索 |
| 财经 | 12 | 财经与商业 |
| 生活 | 3 | 热点线索或垂直补充 |
| 编程 | 5 | 技术与开发者 |
| 外国媒体 | 12 | 权威事实或主流新闻 |
| 公众号 | 105 | 作者观点 / 垂直补充，默认低权重 |

其中 198 条地址使用 `plink.anyfeeder.com` 进行 RSS 转换。它是**分发方式**，不是信息源身份：不能仅用 host 去重、聚类或评分；应以 OPML 标题、上游发布者、feed URL 与后续抓取内容共同识别来源。

### 4.2 数据模型

新增独立目录表，而不把这批公共来源写进某个用户的 `sources` 表：

```ts
interface CuratedSourceCatalogItem {
  id: string;
  name: string;
  feedUrl: string;
  sourceProvider: string | null;       // 如 新华社、36氪、InfoQ
  originalCategory: string | null;     // OPML 原始分类，用于追溯
  preferences: SourcePreference[];
  trustLevel: TrustLevel;
  defaultUsage: SourceUsage;
  topicTags: string[];                 // 人工 / AI 治理后的主题标签
  enabled: boolean;
  verifiedAt: Date | null;
  healthStatus: 'unknown' | 'healthy' | 'degraded' | 'unavailable';
  lastError: string | null;
}
```

同时为产业配置保存“偏好与显式选择”，避免把目录本身复制进配置：

```ts
interface IndustrySourcePolicy {
  preferences: SourcePreference[];
  includeCatalogSourceIds: string[];
  excludeCatalogSourceIds: string[];
  allowAiDiscoveryFallback: boolean;
}
```

现有 `sourceTypes` 可平滑迁移：`authority → authoritative`、`news → mainstream`、`social → trend`、`wechat → creator`、`custom → custom`。`business`、`industry`、`developer`、`research` 为新增的细分偏好。

### 4.3 导入与治理

1. 提供仅管理员可执行的 OPML 导入命令 / 页面，做格式容错、feed URL 去重和预览；不在运行时反复读取文件。
2. 初次导入时保留 OPML 标题、原始分类和 feed URL；先按规则给出初始偏好、可信度与用途，再允许管理员批量修订。
3. 对每条 feed 执行 `checkFeed` 健康检查，记录可用性；失败源不参与默认推荐，但保留记录和错误原因。
4. 为标准 RSS/Atom 提供一个经过测试的通用采集器模板。匹配到目录源时直接复用该模板，而不是请求 LLM 重新生成脚本。
5. 公众号、热点榜单和聚合源默认标为 `supplementary` 或 `discovery`；不能因为 RSS 可访问就升级为高可信主来源。

### 4.4 匹配与回退规则

创建产业配置后，系统先把自然语言描述归一化为关键词、实体、地域、风险词与来源偏好，再对目录源打分：

```text
总分 = 主题标签匹配 + 关键词匹配 + 偏好匹配 + 可信度权重 + 健康度权重 - 去重 / 低质量惩罚
```

默认输出 3–8 个候选源，优先保证至少包含：

- 1 个高可信事实来源；
- 1 个新闻或行业补充来源；
- 管理员明确选择的偏好来源。

在以下情况才自动或显式触发 AI 补源：

- 可用候选源少于 3 个；
- 没有高可信主来源；
- 某个管理员选中的偏好没有覆盖；
- 管理员点击“补充搜索更多来源”。

AI 发现到的非目录来源继续走现有 `findSourcesAgent → generateScriptAgent` 流程。标准 RSS 通过验证后可进入“待治理目录”，由管理员决定是否纳入公共源库。

## 5. 交互与页面重构

### 5.1 建议的页面结构

```text
新增产业信息
  1. 描述产业（必填：名称 + 想关注什么）
  2. 选择信息源偏好（推荐组合，可调整）
  3. 审核监测方案（系统提炼条件 + 预置 RSS 候选源）
  4. 构建信息池（只在有缺口时展示 AI 补源与脚本生成）
  5. 发布与报送（默认折叠，可稍后配置）
```

实现上不必立刻引入新路由：第一阶段可在现有创建页做渐进式披露，并复用现有订阅构建向导。关键是将低频配置从第一屏移走，让用户先看到“系统将监测什么、会使用哪些来源”。

### 5.2 文案与默认值

- “产业说明”改为“你想持续关注什么？”并提供行业化例子。
- “关键词 / 风险词 / 区域 / 关注对象”改为审核结果卡，支持“编辑标签”。
- “信息源类型”改为带用途说明的信息源偏好卡，显示系统默认选择理由。
- 报送默认“工作日 09:00，Asia/Shanghai，每封 10 条”；一分钟调试选项仅在显式测试入口出现。
- 主按钮改为“生成监测方案”，避免让管理员误以为点击后已经发布或已经开始发邮件。

### 5.3 可访问性与防错要求

- 偏好卡使用 checkbox / `aria-pressed` 等可读状态，不能只依赖颜色和对勾。
- 每个自然语言输入提供示例、字符建议和“系统会如何使用这段描述”的说明。
- 审核页明确标注“主来源 / 补充来源 / 线索来源”，防止将热点或公众号当作事实源。
- 发布前显示摘要：产业、监测范围、已选来源数量、AI 补源是否启用、报送默认值。

## 6. 分阶段实施

### 第一阶段：降复杂度，不改变核心数据流

- 重做创建表单为“名称 + 自然语言监测描述 + 偏好卡”。
- 将关键词、风险词、区域、实体和邮件设置移入审核页 / 高级设置。
- 复用现有产业配置字段与现有订阅向导；后端保留兼容的默认值。
- 将分钟级邮件报送从生产创建页移除。

### 第二阶段：导入并使用预置 RSS 源库

- 新增目录表、OPML 导入、健康检查与后台治理界面。
- 提供通用 RSS 采集器模板和预置源匹配服务。
- 在“发现源”步骤先展示目录候选源及其验证状态。

### 第三阶段：把 AI 变成受控回退

- 根据覆盖阈值触发 AI 补源。
- 为目录未覆盖的来源保留现有脚本生成和质量验证。
- 将高质量的 AI 发现结果纳入待审核目录，形成可持续扩充的源库。

## 7. 验收标准与测试

### 产品验收

- 新管理员可在不理解关键词、cron、RSS 或脚本的情况下创建监测方案。
- 第一屏只需要填写产业名称和监测描述；信息源偏好有推荐默认值。
- 用户在进入构建前能看到系统将使用的来源及其角色。
- 预置源足够时，不发生网页脚本生成；覆盖不足时才清晰提示并启动 AI 补源。

### 技术验收

- OPML 导入具有容错、去重、幂等和健康检查测试。
- 目录匹配、偏好打分、回退阈值和来源角色有单元测试。
- 通用 RSS 采集器覆盖 RSS 与 Atom 的标题、链接、发布时间、摘要解析。
- 产业配置旧字段和已有产业数据可无损迁移。
- 创建、审核、发布的 API 对默认值和非法配置有明确校验。

## 8. 已知限制

本提案对现有页面做了代码与流程审查，但当前本地页面无法从审查浏览器访问，因此没有把视觉截图作为 UX 证据。实施前应在可访问的登录态下补一次真实管理员流程走查，重点验证手机端、表单校验、键盘操作、审核页理解度和创建后回到构建向导的衔接。
